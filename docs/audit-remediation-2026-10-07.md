## 对原报告的修正

1. **“Compose 默认 UTC”不符合当前仓库。** 生产 app/worker 已设置 `TZ: ${TZ:-Asia/Shanghai}`。本轮仍显式设置调度时区，覆盖直接启动或定制环境，不能把所有现有 Compose 安装都说成错 8 小时。
2. **“批量转草稿遗留 pendingRevision”不符合当前批量路由。** 非删除操作在事务内遇到 pendingRevision 已整体拒绝，因此没有擅自把待审核修订清空；保护用户未处理的修订比静默删除重要。
3. **PUBLIC_URL 的含义需要纠正配置，而非无条件信任请求 Host。** 当前 canonical/sitemap 的源来自稳定部署配置，这是防 Host 注入/缓存污染的合理边界。反代或隧道应把 PUBLIC_URL 设为公网规范源，内网地址放相应回源配置；目前没有获知用户希望使用的规范域名，因此没有猜测并改写 `.env`。

### 原本运行中的本机部署仍有故障（不能与隔离通过混为一谈）

只读检查 `http://127.0.0.1:8884/api/health` 返回 **500**。系统日志显示旧 `.next` 构建存在 `this.load is not a function`、`renderToPipeableStream is not implemented` 等运行时错误。

`redis-server.service` 处于 failed，日志早在本轮测试之前的 17:08 已明确报错：

```text
Bad file format reading the append only file appendonly.aof.1.incr.aof:
make a backup of your AOF file, then use ./redis-check-aof --fix <filename.manifest>
```

`shibei-worker.service` 因 `127.0.0.1:6379 ECONNREFUSED` 处于反复自动重启状态。
这些不是测试临时 Redis 的问题，也不是“重建空 Redis 就没事”：其中可能有队列、限流、租约等状态，修复前必须保留完整 AOF/RDB。
当前会话 `sudo -n true` 提示需要交互式管理员认证，无法检查受限的数据目录或恢复系统服务。

已准备 **只备份/诊断、不修复** 的脚本，可由用户在本机终端审核后执行：

```bash
# 在项目目录内审核脚本后执行；请勿发送包含凭据的备份。
sudo bash scripts/diagnose-local-redis.sh
```

该脚本会停止故障 worker/Redis，在 `/var/backups/shibei-redis/` 创建并校验完整备份，然后执行**不含 `--fix` 的只读 AOF 检查**。
不会删除、截断 AOF，也不会自动恢复 worker。检查非零退出是损坏诊断结果，不代表备份未完成。
请先依据检查报告评估截断范围/可恢复备份，再决定是否修复；不要发送备份中的 `redis.conf`，它可能含密码。
